# Physics Lab Game — Decisions Log

Working title: **Physics Lab** (Roblox/Minecraft-style digital physics laboratory).
Started: 2026-10-09. Process: spec-driven design (brainstorm → spec → plan → implementation).

## Decided

| # | Date | Decision | Rationale |
|---|------|----------|-----------|
| D1 | 2026-10-09 | Goal: sellable product for schools/universities **and** portfolio piece. | Owner intent. MVP must be demoable to real customers and look polished. |
| D2 | 2026-10-09 | MVP scope = **sandbox core + challenge layer** (enables "class demo" and "assigned lab practice"). Free-play progression is out of MVP. | Challenges are what universities pay for; progression is expensive game design. |
| D3 | 2026-10-09 | Physics scope up to **rigid-body dynamics** (kinematics, projectile, friction, springs, pendulum, energy, collisions/momentum, rotation, torque, moment of inertia, collapsing structures). | Owner wants Besiege/Minecraft-level play. |
| D4 | 2026-10-09 | Use an existing rigid-body engine (candidate: **Rapier**) plus a **validation suite** comparing it against analytic solutions with published tolerances; instruments report measured vs. theoretical error. | Rigor without writing an engine from scratch. |
| D5 | 2026-10-09 | Building model: **hybrid** — voxel grid for terrain/static structures (blocks can be static or dynamic), free mechanical parts with joints (beams, wheels, hinges, springs, counterweights) with grid snapping. | Keeps the Minecraft feel; machines remain real rigid-body physics. |
| D6 | 2026-10-09 | No backend in MVP. Students export a report (PDF/CSV); challenges and results use a **versioned JSON format**. | Cheap pilots, no student personal data; backend/LMS can build on the same formats later. |
| D7 | 2026-10-09 | Platform: **desktop web browser** (Chrome, Edge, Firefox, Safari), mouse + keyboard, including modest laptops and school Chromebooks. | A link is the best sales tool. |
| D8 | 2026-10-09 | Architecture requirement: **render-agnostic, deterministic simulation core** with portable JSON formats, so a future native/installable build only rewrites the presentation layer. | Keeps a later migration cheap (see Deferred F4). |
| D9 | 2026-10-09 | **Bilingual from the MVP (Spanish + English)**: all UI text through i18n from day one, and every challenge/pedagogical text authored in both languages. | Pilots in Latin America and English-speaking markets without a later retrofit. |
| D10 | 2026-10-09 | MVP challenges: **6 built-in experiments** — catapult (projectile), inclined plane + friction, spring launcher (Hooke/energy), cart collisions (momentum), trebuchet (torque/inertia/energy), tipping tower (center of mass). Each has an analytic solver used for validation. | Covers a full first-semester mechanics syllabus up to rigid bodies. |
| D11 | 2026-10-09 | Teacher customization = **"C inside, B outside"**: challenges are pure data (scenario JSON + sensors + parameter bindings + analytic solver id). Teachers set parameter ranges and get a seeded link/file; each student gets distinct values; reports include the seed for verification. | Anti-cheating and course fit now; the full editor later only needs UI. |
| D12 | 2026-10-09 | **Full product vision in the spec, built in phases.** Phase 1 = MVP (D2–D11); every deferred item (F1–F8) is a committed later phase that gets its own spec + plan when its turn comes. | Validate with real users before each phase; nothing is "maybe". |
| D13 | 2026-10-09 | Stack: **TypeScript end to end** — three.js rendering, Rapier (WASM) physics, own voxel mesher. Hard rule: the simulation core is its own package with no DOM/render imports, deterministic, run in a Web Worker. | Fastest iteration; porting the isolated core to Rust stays possible if F4 becomes urgent. |
| D14 | 2026-10-09 | **Accessibility from day one: WCAG 2.1 AA** for all UI, plus accessible alternatives for the 3D canvas (keyboard-operable building, data table for every graph, textual scene-state description, colorblind-safe palette, reduced-motion mode). Produce VPAT/ACR and answer HECVAT before US sales. | US public universities must comply by Apr 26, 2027 (DOJ delay from 2026); procurement requires VPAT/HECVAT. Retrofitting a 3D app is very expensive. |
| D15 | 2026-10-09 | **Realistic measurement uncertainty**: instruments have finite resolution and a configurable, seeded noise model ("ideal" vs "realistic" mode); reports carry uncertainties. | Idealized sims fail to teach error analysis (PhET added noise for this reason); core goal of university labs and a differentiator. |
| D16 | 2026-10-09 | **Cross-platform determinism** for challenges: use `@dimforge/rapier3d-deterministic`, deterministic math in the core (no `Math.sin/cos` for setup), and record app + engine version in every result. | Teachers must be able to replay a student's seeded result exactly; the default Rapier WASM build only guarantees local determinism. |
| D17 | 2026-10-09 | **Engine robustness covered by the validation suite**: solver substeps and bounded mass ratios for the trebuchet (~10:1 guideline), CCD on projectiles, explicit tolerances per benchmark. | Iterative solvers struggle with large mass ratios; fast projectiles tunnel without CCD. |
| D18 | 2026-10-09 | **Performance on school hardware**: performance budget and quality tiers, tested on Celeron-class Chromebooks; render with three.js `WebGPURenderer` (automatic WebGL 2 fallback). | Low-end school devices; WebGPU now ships in Chrome, Safari and Firefox. |
| D19 | 2026-10-09 | **Offline-first PWA** with a download-size budget; app and challenges cached by a service worker. | Poor school connectivity, especially in Latin America; no backend makes offline natural. |
| D20 | 2026-10-09 | **Zero data collection**: no third-party CDNs, fonts or analytics; everything self-hosted; student data stays in local files. | Simplifies HECVAT, FERPA and Mexico's LFPDPPP (Mar 2025). |
| D21 | 2026-10-09 | **Research-informed pedagogy**: implicit scaffolding (affordances/feedback over long text), physics animations as supports, predict → observe → explain loop, a guided **tutorial challenge 0**, and a bilingual **teacher guide** per challenge (answers, syllabus alignment). Result JSON records attempts and predictions as local learning events. | PhET and Physics Playground findings; Algodoo's main complaint is its learning curve; sims complement teachers rather than replace them. |
| D22 | 2026-10-09 | **Greybox first, art direction later**: MVP ships a simple flat low-poly placeholder style with an accessible palette; all visuals go through a swappable **theme layer** (colors, materials, outlines, vector/instrument styles). First implementation milestone = **vertical slice** of the catapult challenge end to end (build → predict → launch → measure → report) in greybox. | Owner wants to see the whole engine working before committing to an art style. |
| D23 | 2026-10-09 | **Simulation core design approved**: SI units; voxel grid with 0.5 m blocks (static blocks merged into compound colliders, dynamic blocks as individual bodies); parametric parts on a 0.1 m snap; joints = fixed, hinge, slider, spring (explicit k and damping); serializable **Command pattern** for every change (undo/redo, exact replay, future multiplayer); Build vs Run modes; fixed 1/240 s step with CCD and solver substeps; slow motion changes steps per frame, never dt; declarative sensors read ground truth, `instruments` adds noise; seeded PRNG and own trig; core runs headless in Node/CI. | Section 2 of the design review. |
| D24 | 2026-10-09 | **Minecraft-style command console in the MVP**: text commands parse into the same serializable commands as the mouse UI (`/summon`, `/fill`, `/set`, `/physics`, `/time`, `/give`, `/measure`, `/seed`, `/record`), relative `~` coordinates and selectors (`@selected`, `@all[type=…]`, `#id`); English canonical names with autocomplete, history and bilingual help; **per-mode permissions** (challenges lock commands such as `/physics gravity` or `/set mass`). | Power users and teachers, keyboard/screen-reader accessibility, shareable setups, scripted tests. |
| D25 | 2026-10-09 | **Challenge & data flow approved**: challenges are versioned JSON (scenario + locks, parameter bindings with ranges/units/distributions, bilingual tasks with tolerance defaulting to combined uncertainty, solverId, instrumentMode, allowedCommands). Teacher shares a URL-embedded challenge or `.json` file; per-student seed = teacher seed + student ID; student loop predict → build/run → observe (measurement ± u) → compare prediction/theory/measurement → explain → export PDF + CSV + result JSON (versions, seed, predictions, **command log**, measurements, learning events). **Replay verification**: the teacher view re-runs the command log deterministically to detect edited results. Long URLs fall back to files; version mismatches warn and migrate; generator validates parameter ranges with the solver. | Section 3 of the design review. |
| D26 | 2026-10-09 | **Browser experience approved**: Home / World (Build, Run, Teacher view) / contextual side panel with challenge loop and notebook-calculator; orbit camera **and first-person walk mode in the MVP** (WASD, jump, crouch, sprint, creative-style flight via double-tap jump in sandbox; player is a Rapier kinematic character controller — in challenge Run mode the player never collides with or pushes experiment objects, so replays stay deterministic; sandbox runs where the player pushed objects are flagged non-verifiable); hotbar, join tool with visible snapping, `/` or `T` console, undo/redo; instruments shown as `value ± u` with accessible data tables; WCAG 2.1 AA (keyboard, screen-reader scene-state region, AA contrast, colorblind-safe, reduced motion); es/en with locale number formatting; theme tokens; three quality tiers auto-selected by FPS — budget 60 fps with ~300 dynamic bodies on medium, ≥ 30 fps on Celeron Chromebooks; offline PWA with ≤ 15 MB compressed initial download; React UI kept outside the three.js canvas. | Section 4 of the design review. |
| D27 | 2026-10-09 | **Quality & delivery approved**: per-package test strategy (schemas/migrations/golden files; command, determinism-hash and engine-validation tests; property-based solver-vs-simulation sweeps; statistical noise tests; console parser/permission tests; component, axe-core + manual a11y, i18n completeness, milestone-end Playwright e2e, Chromebook benchmarks; CI with bundle budget). Phase 1 milestones M1 vertical slice → M2 full builder → M3 content → M4 teacher flow → M5 pilot-ready; art direction (F11) in parallel from M2. | Section 5 of the design review. |
| D28 | 2026-10-09 | **Dedicated repository** `physics-lab` created; design docs live in `docs/design/`. Each Phase 1 milestone gets its own implementation plan, starting with M1. | Owner moves development here; Phase 1 is too large for a single plan. |

## Deferred (revisit later — do not lose)

| # | Topic | Options considered | Trigger to revisit |
|---|-------|--------------------|--------------------|
| F1 | **Free-play progression** (unlocks, goals, rewards) to make it a standalone game. | Layer on top of the challenge system. | After MVP pilots validate the challenge loop. |
| F2 | **Kids mode** (basic version for young children). | Separate presentation layer (UI, copy, simple challenges) over the same engine; needs its own pedagogy design (age, reading level, motor skills). | After university MVP; pair with touch support (F5). |
| F3 | **Teacher backend / accounts** (groups, assignments, dashboard) and **LMS integration (LTI: Moodle, Canvas)**. | Own backend vs. LTI. Both consume the D6 JSON formats. | When pilots need scale or institutions request grade sync. |
| F4 | **Installable / higher-performance build**. | (a) Tauri/Electron wrapper — days, offline/installable, little perf gain; (b) Tauri + native Rapier (Rust) physics with web rendering — weeks; (c) full native engine (Godot/Unity/Bevy) — months, rewrites rendering/UI/tools. D8 keeps all three viable. | When web performance limits real use (e.g. > several hundred dynamic bodies) or offline install is requested. |
| F5 | **Tablets / touch controls**. | Separate control scheme for 3D building. | Together with kids mode (F2). |
| F6 | **Multiplayer** ("classroom rooms" rather than open Roblox-style servers). | Requires backend (F3) and moderation if minors are involved. | After F3. |
| F7 | **Infinite / large voxel worlds** (chunking, streaming). | Fixed-size editable world in MVP. | If level design needs larger worlds. |
| F8 | **Full challenge editor (committed — owner wants it)**: teachers build scenarios in the sandbox, define sensors, tolerances, bilingual texts, locks. | Hard part: ground truth for arbitrary scenarios — teacher-supplied formula (expression parser), simulation-as-truth (loses prediction-vs-theory contrast), or solvability checks. D11 data model already supports it. | First milestone after the MVP. |
| F9 | **Pilot efficacy study**: Force Concept Inventory pre/post with normalized gain (Hake) in real courses. | Produces our own evidence (POE/simulation evidence in the literature is thin) and sales material. | During the first university pilots. |
| F10 | **Business model and pricing**. Reference points: Pivot Interactives ~US$10/student/semester (higher ed), Labster from ~US$49/student. | Per-seat vs institutional license vs freemium. | Before the first paid pilot. |
| F11 | **Art direction**. Candidates: Wind Waker-style flat cel shading (cheapest), BotW-style painterly cel shading with quality tiers, Sea of Thieves (too expensive for Chromebooks). Favourite concept so far: "toy world + engineer's notebook" — warm toon low-poly islands, wood-and-brass toy parts, and a signature **Blueprint Mode** that unfolds the scene into a cyanotype engineering drawing with hand-inked free-body diagrams, dimensions and ± uncertainties (bridges real scene → force diagram). Instruments styled as notebook sketches; vectors distinguished by color **and** shape. | Theme layer (D22) makes it a drop-in change. | After the greybox vertical slice runs. |
| F12 | **Command scripting**: `.mcfunction`-style function files and in-world command blocks for automation. | Feeds the full challenge editor (F8). | With or after F8. |
